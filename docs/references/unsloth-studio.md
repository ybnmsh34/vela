# Reference study: Unsloth Studio

Study A, Phase 1 reference study for Vela. Researched first-hand from Unsloth's own docs, GitHub repo, and public issue tracker (dates below are fetch dates in Aug 2026). Unsloth Studio is under active beta development, so exact UI details may drift; every claim below is tied to a specific fetched source, and anything I could not verify against a primary source is flagged **UNVERIFIED**.

## What it is

Unsloth Studio is a real, distinct product from the Unsloth fine-tuning library — not a rebrand of it. Unsloth (the org) now ships three things: **Unsloth Core** (the Python/PyTorch fine-tuning library people already know), **Unsloth Studio** (a local web UI/server for training, running, and exporting models), and **Unsloth Desktop** (a native Tauri wrapper that packages Studio) [^1][^2].

Concretely, Studio is:
- A **local client-server web app**. `unsloth studio` starts a Python backend on `127.0.0.1:8888` (FastAPI, per repo-derived docs) and you open it in a browser; first launch forces you to set a password, auth is JWT-based (`/api/auth/*`), and all other API routes require a Bearer token [^3][^2].
- Wrapped by **Unsloth Desktop**, a Tauri app (Rust shell + the same React frontend in a native window) — explicitly "Tauri based," not Electron [^18]. The Rust shell does hardware preflight checks, owns the Python backend process lifecycle, adds native file dialogs/clipboard, a custom titlebar, a one-time local auth token for shell↔backend loopback communication, and a multi-tier auto-updater (app shell via `tauri-plugin-updater` against GitHub releases, plus an independent updater for the bundled `llama.cpp`/`whisper.cpp` binaries) [^19].
- **Stack**: React frontend using Tailwind CSS, Zustand for state, and TanStack Router for navigation; Python backend; inference powered by `llama.cpp` (GGUF) and Hugging Face `transformers`/TRL for training; Data Recipes powered by NVIDIA NeMo/DataDesigner [^5][^2][^1]. The GitHub repo layout confirms this split at `studio/backend`, `studio/frontend`, `studio/src-tauri` [^6].
- **Licensing**: the core `unsloth` package is Apache-2.0; the Studio UI specifically is dual-licensed and ships under AGPL-3.0 [^1][^2].
- Launched publicly in **March 2026** per the GitHub Discussions announcement, still labeled "Beta" as of this writing [^7][^1].
- It is model-agnostic in scope beyond LLMs: text, vision, TTS/audio, embeddings, and (per a dedicated doc page) image/video diffusion models (FLUX, Qwen-Image, SDXL, etc.) [^1][^8].

So: this is not "the fine-tuning library with a new name." It's a separate local web application (optionally desktop-packaged) that wraps the library for no-code training, and separately does local inference/chat, dataset building, and model export — i.e. a full local ML workbench, not a chat client.

## Information architecture

Studio's navigation is a **left sidebar** (`AppSidebar`) plus a top `Navbar`, driving a small number of top-level routes. From the repo-derived route/tour mapping and the docs' own workflow description, the top-level places are [^9][^3][^1][^8]:

- **Chat** (`/chat`) — the landing surface. Docs state plainly: "the Unsloth app should now open on the Chat Page" after first login [^10]. A left-sidebar "New Chat" link returns here from anywhere [^3].
- **Images** — a separate top-level sidebar destination for diffusion image generation, distinct from Chat. Confirmed verbatim in the docs: "Select Images from the sidebar. The Create workflow opens by default." [^8] Inside it: Create/Transform/Inpaint/Extend/Upscale/Reference/Edit workflows (unsupported workflows for the loaded model are auto-hidden), an image-model picker, and a local Gallery of past generations [^8]. This is a genuine top-level area, not a mode within Chat.
- **Studio / Train** (`/studio`) — the fine-tuning workspace. Docs describe it as having "4 main areas: Model, Dataset, Parameters, and Training/Config" [^3].
- **Data Recipes** — a separate visual, graph-node workflow editor for turning raw documents into training datasets; recipes are stored locally in the browser and listed on their own page [^3].
- **Export** (`/export`) — convert/save a trained or existing model to GGUF, merged safetensors, or LoRA-only, and choose local save vs. push to Hugging Face Hub [^11][^3].
- **Settings**, tab-structured (confirmed by a `SETTINGS_TAB_MENU_ITEMS` sidebar menu in the frontend code) — includes at least a **System** tab, where the GGUF inference engine backend (CPU/CUDA/ROCm/Vulkan) can be changed and applied [^18], an **API** tab for key management and the API/MCP monitor [^20], and a **Connections** tab (API providers and model servers) [^12][^9].
- **Model Arena** — not a separate route but a chat-page capability: run the same prompt against two models side by side (e.g., base vs. fine-tuned adapter) [^10].

A first-time user's reported experience (GitHub issue) corroborates a small number of persistent tabs that you switch between (Data Recipes / Export / others), with state sometimes bleeding across tab switches (see Failure surfaces) [^13].

**Data Recipes input formats, precisely**: the Data Recipes quickstart names PDF and CSV explicitly — "Unsloth Data Recipes lets you upload documents like PDFs or CSVs files" [^3]. A separate features blurb on the Studio overview page additionally lists JSON for Data Recipes by name — "Data Recipes transforms your docs into useable / synthetic datasets via graph-node workflow. Upload unstructured or structured files like PDFs, CSV and JSON" [^1]. DOCX is documented elsewhere in Studio (the Train tab's local-dataset uploader accepts PDF/DOCX/JSONL/JSON/CSV/Parquet [^3]), but I found no Data-Recipes-specific statement that DOCX is accepted there — that part is **UNVERIFIED**.

## Model as an object

Studio treats "a model" as a first-class object with identity, location, download/load state, and declared capabilities — this is one of its most transferable ideas:

- **Selection**: a "Select model" combobox in the top-left of the Chat page lets you type any Hugging Face model name or search the Hub directly; local files under `~/.unsloth/studio/models` and your existing Hugging Face cache are auto-discovered and appear in the same list, alongside external/API-connected models under a separate "Connected"/"External" grouping [^10][^14].
- **State transitions are explicit and shown to the user**: selecting a model variant triggers a visible download, then a load-into-memory step, then an explicit "confirmation" state before you can chat [^10].
- **Capability is declared per-model, not implicit**: GGUF-format entries are explicitly excluded from the training flow ("GGUF format models are excluded from training - they are inference only") [^3]. For training, picking a model auto-fetches its config from the backend and pre-fills hyperparameter defaults; for image models, the doc explicitly says "unsupported workflows are hidden automatically" depending on what the loaded model supports (e.g., only Qwen-Image-Edit/FLUX.1 Kontext expose instruction-based edit) [^8][^3].
- **Hardware fit is surfaced on the model itself**: for GGUF quantizations, Studio marks the size it recommends for your hardware, and marks others **TIGHT** ("may use system memory and run more slowly") or **OOM** ("unlikely to fit") [^8]. This exact labeling confused a first-time user in practice — the in-app "Tour"/"Learn more" affordances didn't explain what OOM/TIGHT/GGUF meant [^13].
- **Multi-provider identity**: local GGUF/safetensors, HF Hub models, and externally-connected provider models (OpenAI, Anthropic, Ollama, vLLM, llama.cpp servers) all populate the same model picker once connected via Settings → Connections, so "which model am I talking to" stays a single selector regardless of where the model actually runs [^12][^14].
- Gated models (Llama, Gemma, etc.) require a Hugging Face token, which is **validated in real time with an inline error if invalid** — capability-gating gets immediate feedback rather than a failed download [^3].

## Long-running work

Studio has two long-running-work idioms, both fairly explicit — one for downloads/model loads, one for training:

- **Downloads/loads**: clicking a model variant starts a download indicator; loading into memory follows, then a confirmation state [^10]. A real user asked for an ETA/speed indicator, implying the default download indicator does **not** show ETA or throughput [^13]. The main repo's recent changelog claims work on "recover stalled downloads and reuse existing GGUF files," implying earlier versions did not reliably resume failed downloads [^1]. A separate bug report shows model *installer* downloads (PyTorch, the package itself) failing mid-stream on flaky connections with no resume, forcing a full reinstall — though the installer itself is described as rollback-safe ("preserving existing environment for rollback... restored previous environment") [^15].
- **Training**: clicking "Start Training" shows a **full-page overlay** with an animated terminal-style log of phases (Downloading → Loading → Configuring → Training, each color-coded), with an explicit **cancel button (×)** that raises a confirmation dialog before stopping anything [^3]. Once the first training step lands, the overlay is replaced by a live view: a status panel (epoch, step progress bar, loss, LR, grad norm, elapsed/ETA/steps-per-second/tokens) and a GPU monitor (utilization, temperature, VRAM, power) polled every few seconds [^3]. Stopping mid-run offers a **choice**, not a single cancel: "Stop & Save" (checkpoint first) vs. "Stop" (immediate, no checkpoint) [^3]. Docs also claim you can watch training progress from another device (e.g., phone), which — combined with the client-server architecture (training runs in the Python backend, UI is a client polling/streaming state) — implies training is not tied to the browser tab being open, though I did not find an explicit statement of "what happens if you navigate away" and mark that inference as **UNVERIFIED** beyond the architectural implication [^3][^1].
- Training also exposes an **SSE stream** endpoint (`GET /api/train/stream`) plus polling endpoints for status/metrics, and separate start/stop/reset REST endpoints — i.e., the long-running job is a server-side resource with its own state machine, independent of any one client connection [^3].
- Data Recipes runs (dataset-generation graph workflows) similarly separate "preview" (fast, sample rows) from "run full dataset build," with progress viewable "live in graph or in Executions view" [^3].
- Chat itself is a long-running operation too: a later changelog entry states Studio can "run multiple conversations at once. Starting a New Chat leaves the previous answer generating, and each active conversation gets its own progress indicator and Stop control," backed by "4 llama-server slots by default, adjustable in the web UI," with tools/uploads/agents "isolated between chats" and one chat's Stop not interrupting others [^27].

## Failure surfaces

Failure handling is a mix of inline validation, transient toasts, and terminal-style install logs — with real, documented rough edges:

- **Inline validation before you can act**: the "Start Training" button stays disabled until model + dataset are both configured; validation errors (e.g., eval steps set without an eval split, vision dataset paired with a text-only model) appear inline near the relevant field [^3]. Invalid Hugging Face tokens are flagged inline in real time [^3].
- **Toast-style runtime errors that are reportedly too transient**: a first-time user hit `Failed to load model: llama-server failed to start. Check that the GGUF file is valid an...` as a popup that appeared "in place of the download indicator, but quickly went" — they could not read the full message before it disappeared [^13]. The same user reported a UI bug where the Data Recipes and Export tabs would render duplicated content after switching tabs and back [^13].
- **Install-time failures use a terminal-style log with named causes and safe rollback**: a documented failure (`unsloth studio` install hitting a PyPI timeout) prints a chained error (`Failed to fetch: https://pypi.org/simple/unsloth/` → `client error (Connect)` → `operation timed out`) and explicitly reports `restoring previous environment after failed install... restored previous environment` — i.e., failed installs/updates are designed not to corrupt the existing environment [^16].
- **A dedicated Troubleshooting & FAQ docs page** exists as an external reference (not in-app help), organized as a flat list of known issues (OOM during eval, CUDA asserts, stuck-at-90% downloads, slow Unsloth, locale errors, etc.) rather than contextual in-app guidance [^17].
- **Connections/provider failures** get a documented, specific troubleshooting note: "If a provider fails to connect, check that the API key belongs to the selected provider and has access to the model you chose," and if a model doesn't appear after "Reload Models," Studio falls back to its own default model list rather than blocking you [^12].
- **API-endpoint failures are also documented per symptom**, not just as generic errors: `401 Unauthorized` means a missing/wrong `Authorization` header; `Lost connection to the model server` means the underlying llama.cpp process crashed or its tab was closed inside Unsloth; a client silently receiving a single JSON blob instead of SSE means it hit the wrong path or is buffering instead of streaming; a cut-short reply is diagnosed by checking "Context used" in the API monitor for a value near 100% or a `stop_reason` of `length` [^20].
- No evidence of a centralized error/notification history (e.g., a bell icon or error log panel) was found in any fetched source; errors described are all point-in-time toasts or inline messages. **UNVERIFIED** whether a persistent error log exists in the UI.

## Local API, tool-calling, and agent integration

This section extracts specifics the coordinator asked for by item number, all cited to sources fetched for this pass. Where a claim rests on an automated full-page read (WebFetch) rather than my own direct extraction, that is noted explicitly — those reads are of the actual fetched page/PR content, not general-knowledge inference, but I could not personally re-verify every line, so treat verbatim-looking quotes from those reads with slightly less certainty than the ones I extracted myself.

### 1. The dual local endpoint

Confirmed directly and in detail [^20]. Loaded models (including GGUFs) "are exposed as an authenticated API via `llama-server`. A long API key is generated for security reasons like how OpenAI provides one." The key architecture: **"Unsloth speaks two dialects on the same port."** Both endpoints support streaming, tool calling, and vision inputs:
- Anthropic-compatible `/v1/messages` — for Claude Code, OpenClaw, the Anthropic SDK, "and any client that expects the Messages API."
- OpenAI-compatible `/v1/chat/completions` and `/v1/responses` — for the OpenAI SDK, OpenCode, Cursor, Continue, Cline, Open WebUI, SillyTavern, "and any OpenAI-compatible tool."

Routing is by **path**, not by port or process: "You don't need to run different servers for the two formats. Unsloth handles both on the same port." [^20] Authentication is a **single shared bearer key** for both dialects: "Authenticate with an `Authorization: Bearer sk-unsloth-…` header on every request." [^20][^21] Keys are created from Settings → API, are shown once, only a hash is stored server-side, and a revoked key fails closed with `401 Unauthorized` on every subsequent request [^20].

### 2. The exact `tool_choice` mapping

Confirmed **verbatim**, exactly as the spec states it. Quoting the source directly: "If you're using the Anthropic `/v1/messages` endpoint, `tool_choice` maps cleanly: Anthropic `auto` → OpenAI `auto`, Anthropic `any` → OpenAI `required`, Anthropic `{type: "tool", name: "x"}` → OpenAI `{type: "function", function: {name: "x"}}`, Anthropic `none` → OpenAI `none`." [^20] No correction needed — the mapping given in the brief is accurate to the letter.

### 3. The Anthropic SSE event shape

Partially confirmed, with a caveat. My own direct extraction of the curl/HTTP recipe page returned only headings (the actual code-tab bodies did not survive text extraction); a full-page automated read of the same URL reported the documented event sequence as: **"Events follow Anthropic's SSE shape: `message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`, plus Unsloth's custom `tool_result` event for server-side tool output."** [^21] This is internally consistent with Anthropic's own public Messages API event names, and with a separately, directly-confirmed statement from the API guide: **Unsloth's own server-side tools (Python, web search, bash) execute server-side and "stream the results back as `tool_result` events. The model sees each tool's output on its next turn."** [^20] I could not find, in any source fetched, the exact client-side follow-up message shape for carrying an Anthropic-style tool result back to `/v1/messages` (i.e., the `{"type": "tool_result", "tool_use_id": ...}` content-block structure) — that specific shape is **UNVERIFIED**. (For the OpenAI dialect, by contrast, Unsloth's own published code sample shows this exactly: a follow-up message of `{"role": "tool", "tool_call_id": _id, "name": fx, "content": str(out)}` [^26].)

### 4. The base_url rule

**Confirmed for the Anthropic side, directly and literally.** Unsloth's own Claude Code setup guide shows the exact environment variable value used to point the Anthropic SDK/CLI at a local Unsloth server: `export ANTHROPIC_BASE_URL="http://localhost:8888"` — **no `/v1` suffix** [^23]. The equivalent PowerShell form is `$env:ANTHROPIC_BASE_URL = "http://localhost:8888"`, also without `/v1` [^23]. This is paired with an empty `ANTHROPIC_API_KEY` (so Claude Code doesn't prompt for a cloud key) and `ANTHROPIC_AUTH_TOKEN` set to the `sk-unsloth-…` key [^23].

**For the OpenAI side, I could not find an Unsloth doc page that shows a literal `OPENAI_BASE_URL=http://localhost:8888/v1` example against Unsloth Studio's own default port.** What I *can* confirm: Unsloth's own published tool-calling code sample instantiates the OpenAI Python SDK against an OpenAI-compatible `llama-server` with `base_url = "http://127.0.0.1:8001/v1"` — **with the `/v1` suffix** [^26]. That example targets a standalone `llama-server` on port 8001 (a separate tutorial setup), not Unsloth Studio's own multiplexed port 8888, but it demonstrates the same general rule: the OpenAI SDK does not itself append `/v1`, so the caller must include it in `base_url`, while the Anthropic SDK's base URL is bare and the SDK appends the full path itself. Given `/v1/chat/completions` and `/v1/responses` are the documented OpenAI-compatible endpoint paths on Unsloth Studio's own port [^20], the same `/v1`-suffixed convention would apply there too — but I am marking the Unsloth-Studio-specific instance of this as **UNVERIFIED** since I did not find it stated literally for port 8888. The asymmetry itself (Anthropic: no `/v1`; OpenAI: `/v1` required) is confirmed as real and is exactly the kind of trap the coordinator described.

### 5. The bind-address tool policy

**Confirmed verbatim, including the stated rationale.** From the API guide's "Server-side tool policy" section [^20]:

> `unsloth run` controls whether server-side tools (web search, code execution, etc.) are exposed by the inference server. Defaults are based on the bind address:
> - `127.0.0.1` (localhost) — tools on by default. Only your machine can reach the server.
> - `0.0.0.0` or any non-loopback address — tools off by default. **A leaked API key on a network-exposed server means arbitrary code execution on the host.**
>
> Flags: `--enable-tools` / `--disable-tools` — force on or off. On `0.0.0.0`, `--enable-tools` shows a y/N security prompt. `--yes` / `-y` — skip the prompt (for automation).
>
> The resolved policy is a **process-level hard override** — individual requests cannot bypass it via `enable_tools=true` in the request body.

This is exactly the reasoning the coordinator described ("a leaked key on an exposed port is remote code execution"), stated by Unsloth itself, and the enforcement point (process-level, not per-request) is explicit.

### 6. `unsloth start <agent>` mechanics

Confirmed in detail [^22]. `unsloth start <agent>` (agents: `claude`, `codex`, `hermes`, `openclaw`, `opencode`, `pi`) "automatically configures the endpoint, API key, provider, model, and context length for each launch" and "uses temporary or session-scoped provider configuration. It does not add an Unsloth provider to the agent's normal configuration files." [^22] Key documented options: `--model`/`-m` (select a model; without it, uses the first model Unsloth reports), `--api-key` (or `UNSLOTH_API_KEY` env var), `--launch`/`--no-launch` (print the generated env+command instead of running it — "The output can contain connection credentials, so do not publish it in logs or screenshots"), `--serve`/`--no-serve` (allow/prevent auto-starting a temporary local server), `--gguf-variant`, `--context-length`/`--max-seq-length`, `--persist`/`--no-persist` (per-agent — Claude Code and OpenCode keep their own session store and don't need it; Codex, OpenClaw, Hermes, and Pi use temporary managed homes by default and do need it to resume), and `--yolo` ("maps to the selected agent's trust or non-prompting mode... Only use it in an environment where unrestricted agent actions are acceptable") [^22]. Arguments that aren't recognized Unsloth options "are passed to the selected agent" [^22].

**`--disable-tools` passthrough, precisely:** I found `--disable-tools` documented as a flag on the **Unsloth server process itself** (i.e., `unsloth run`/`unsloth studio`, invoked when a model is loaded), not in `unsloth start`'s own options table [^22][^23]. The Claude Code guide states it plainly, under "tune the Unsloth server": "By default Unsloth Studio runs its own server-side tools, which swallows the agent's tool calls, so Claude Code answers but never edits files. `--disable-tools` switches to passthrough, so Claude Code's own Write/Edit/Bash tools are used." [^23] I did **not** find explicit documentation that `unsloth start` itself forwards an unrecognized `--disable-tools` flag through to the server it may auto-spawn — the two commands are documented separately, and whether `unsloth start`'s "temporary server" auto-launch path (triggered by `--model` when no server is running [^22]) inherits or exposes this flag is **UNVERIFIED**. What is clear and confirmed: the *effect* described — disabling Unsloth's own server-side tools so an external agent's native tools aren't swallowed — is real, documented, and directly relevant to any Vela integration with external coding agents.

### 7. Self-healing tool-call repair

Confirmed from three independent, directly-fetched sources, with consistent numbers [^10][^20][^27]. Framing: broken/malformed tool calls are reduced "by 50%" [^20]; across models, tool calls are "30% to 80% more accurate" [^10]. Documented mechanics:
- **Detection/repair target**: malformed tool-call XML/markup leaking into chat output. A published before/after test (model: `unsloth/Qwen3.5-4B-GGUF`, quant `UD-Q4_K_XL`, web search + code execution + thinking enabled) shows XML leaks in response dropping from 10/10 runs to 0/10 [^10].
- **Retry/termination**: "The maximum number of allowed tool calls is more than 25" [^10]; the changelog is more specific — "Number of tool calls allowed are increased to 25 from 10" and "Tool calls now terminate much better, so looping / repetitions will be reduced" [^27]. So termination is bounded by a hard cap on total tool calls per turn/response, raised over time (10 → 25+), plus unspecified internal loop-detection ("terminate more reliably, reducing loops and repeated calls" [^10]) — the exact loop-detection algorithm is **UNVERIFIED**.
- **Dedup**: "Improved tool-call healing and deduplication logic helps prevent XML from leaking into outputs" [^10][^27] — deduplication is named explicitly as distinct from healing, but the dedup mechanism itself (e.g., hashing repeated calls, diffing arguments) is not detailed in any fetched source — **UNVERIFIED** at that level of detail.
- Side effects measured in the same test: average tool calls per run dropped 5.5 → 3.8, and average response time dropped 12.3s → 9.8s [^10], suggesting healing reduces wasted/retried calls rather than just cleaning output after the fact.

### 8. The AST sandbox, the permission selector, and the documented bypass (issue #4818)

**The permission selector, confirmed verbatim.** Unsloth's own changelog describes a redesign from a binary toggle to a graded control: "The old bypass toggle is now a four-level permission selector: **Ask**: approve every tool call. **Approve for me**: automatically run read-only actions and pause for potentially unsafe ones. **Off**: disable tool calls. **Full access**: allow all calls and disable the sandbox. These controls cover terminal, Python, web search, RAG, and MCP tools." [^27] A separate, earlier Desktop doc page describes the same underlying choice in softer terms — "Unsloth can run tools inside a secure sandbox environment to protect your system, or, if you prefer, you can allow it to directly access and edit your files" [^33] — consistent with, and likely a plainer description of, the same Ask/Approve/Off/Full-access control.

**The bypass — issue #4818 — read in full via the GitHub API, not just the rendered page.** Title: *"[Bug] [Security] Unsloth Studio: Code execution (terminal) tool sandboxing can be bypassed to allow privileged commands like sudo/chmod."* [^28] The reporter's original body is thin ("I just started playing around with the tools in the chat page on Unsloth Studio and noticed the sandboxing isn't robust and can be bypassed... Attached images for a clearer explanation" [^28]), but the comment thread is not: a maintainer (`rolandtannous`) initially asked for a reproduction, cautioning that small LLMs can hallucinate access they don't have; the reporter (`xyehya`) directly rebutted that this was **verified independently of the model's own claims**: *"its not about seeing the file. the terminal command actually ran and i verified it (the chmod +x succeeded and the execute bit was set on the actual file on disk)... my analysis was not based on the LLMs output solely."* [^29]

**Exact class of escape** (from a full-content, automated read of the fix PR's actual diff and description — not my own line-by-line read of the PR, so treated as a secondary source, but grounded in the real PR content rather than general knowledge) [^30]: the original sandbox used **naive string-based command filtering** — `str.split()` tokenization — which failed to catch full binary paths (`/usr/bin/sudo`), shell quoting/escaping, nested shells and process substitution (`bash -c 'sudo ...'`), and cross-tool pivoting through Python's `os.system()`/`subprocess` (including aliased imports like `from os import system`). This matches the spec's framing exactly: a sudo/chmod-class privilege-escalation bypass of a naive command-string sandbox.

**The fix (PR #4827)** is described as six layered defenses, not one patch [^30]: `shlex.split()`-based tokenization plus path/shell-boundary normalization; environment sanitization (stripping `HF_TOKEN`, `WANDB_API_KEY`, `AWS_*`); Linux kernel-level restriction via `PR_SET_NO_NEW_PRIVS` (so `sudo`/`su` fail regardless of invocation path) plus resource limits (`RLIMIT_NPROC=256`, `RLIMIT_FSIZE=100MB`); AST-based static analysis that detects `os.system`, `os.popen`, `subprocess.run`/`Popen`, `os.exec*`/`spawn*`/`posix_spawn*` calls (including through aliased imports) carrying blocked commands or dynamic arguments; cross-platform handling (`cmd /c` on Windows, `bash -c` on Unix, with platform-specific added blocklist entries like `rmdir`, `takeown`, `icacls`, `powershell` on Windows); and an expanded blocklist (7 → 14+ commands, adding `su`, `chown`, `passwd`, `mount`, `umount`, `fdisk`, `kill`, `killall`, `pkill`) [^30]. **This is the origin of "AST" in this system**: AST-based static analysis is one of six defenses added specifically by the security fix — I found no evidence that Unsloth markets or documents "the AST sandbox" as a standalone, named product feature anywhere; it's an internal implementation detail surfaced by this PR's review.

**Status — fixed, mitigated, or open, precisely**: the issue was formally **closed the same day it was opened** (created `2026-04-03T06:25:33Z`, closed `2026-04-03T20:33:45Z`, closed by `danielhanchen`, `state_reason: "completed"`) [^28], which lines up with PR #4827 having merged April 3, 2026 [^30]. **But the reporter's own final comment, posted the next day — after the issue was already closed — reads: "Getting better but still not there :) A good starting point / reference: https://flatt.tech/research/posts/pwning-claude-code-in-8-different-ways/ or might as well just go for nvidia openshell https://github.com/NVIDIA/OpenShell"** [^29]. So: **mitigated, not fully closed**, by the original reporter's own assessment, even though the tracker shows it as completed. The PR analysis independently reaches the same conclusion: "layered mitigation rather than complete closure of the vulnerability class... sophisticated attackers might discover novel escape mechanisms through features not explicitly tested" [^30]. For a sandbox Vela builds to resist this class of attack, the operative lesson is **the fix approach (defense-in-depth: tokenization + OS-level privilege denial + static analysis + blocklist), not a claim that the vulnerability class is closed.**

### 9. Canvas

Confirmed from two independent, directly-fetched sources. The overview page: "Unsloth creates a sandbox to allow GLM-5.2 to execute code which shows as HTML preview in Canvas." [^1] The changelog, describing the feature's introduction and later refinement: an early entry — "Opens generated HTML in a dedicated canvas panel inside Unsloth Studio. Supports interactive outputs, including browser based visualizations and CDN-loaded packages. Lets you switch between rendered preview and source code." [^27] — and a later entry confirming the rename/consolidation: "Chat 'artifacts' are now canvas, with inline HTML canvas cards that auto-render, a Code view, and DiffusionGemma keeps its raw code visible inline instead of collapsing." [^27] So: Canvas auto-renders generated HTML inline as a card, with an explicit toggle to a Code view showing the raw source — exactly the two-mode (rendered/source) structure the coordinator described.

### 10. MCP support

**HTTP/SSE with OAuth and custom headers — confirmed directly, this is the currently-documented path.** The dedicated MCP guide's "Adding custom MCP servers" flow: fill in a display name and "URL: the server's base endpoint, e.g. `https://mcp.vercel.com`"; then either "turn on Use OAuth sign-in" for servers needing browser-based auth (GitHub, Linear, Vercel, etc.) — "A browser window will open on first connect so you can authorize Unsloth" — or, for token-based servers, "leave OAuth off and click Add header under Custom headers. Add an `Authorization` header with your token." [^24] Each server gets its own on/off toggle plus tool-refresh/edit/delete controls, gated by a master "Use MCP Servers" toggle; Unsloth ships with built-in presets for Context7, Exa, and Hugging Face [^24].

**stdio — the gap in issue #5936, and what actually happened afterward.** The issue, read via the GitHub API: title "*[Feature] Support stdio MCP servers via a config file*," body states plainly: "Unsloth Studio currently only supports remote MCP servers added via HTTP/SSE URLs through the UI... locally installed stdio-based servers (node scripts, python scripts, uv-managed tools) cannot be used directly. Users must run a separate bridge tool (e.g. `supergateway`)... Every other client that supports MCP implements both transports. Unsloth Studio is currently the only one that does not." [^31] **This was subsequently resolved, per the issue's own comment thread** (fetched via the GitHub API): a maintainer (`rolandtannous`) commented "#5863 added native stdio MCP support. the code spawns local processes via fastmcp's `StdioTransport` directly, gated by `UNSLOTH_STUDIO_ALLOW_STDIO_MCP=1` (set automatically by the desktop app). So no supergateway bridge is needed anymore." [^31] A follow-up PR (#5943) was flagged for community testing; the reporter (`shashwata2020`) confirmed "the stdio mcp server import via config file works" but flagged a real UX bug (bulk-import of all configured servers only appeared after adding one manually, plus a couple of unrelated reasoning-display bugs) [^31]; a later comment says that UX bug was "Added in #6030" (i.e., fixed) [^31]. This matches an otherwise-easy-to-miss changelog line from the same period: "**Local command-based MCP server support**" listed alongside "Remote MCP server support, including custom headers and OAuth" and "MCP can now be turned on from the chat composer" [^27]. **Discrepancy I could not fully reconcile**: the current, freshly-fetched dedicated MCP walkthrough page ([^24], fetched today) documents *only* the URL/OAuth/header flow and does not mention command-based/stdio configuration anywhere in its walkthrough, even though the issue thread and changelog both indicate stdio support shipped months earlier. I'm treating stdio MCP support as **real and shipped** (strong evidence: specific PR numbers, an explicit env var, a named library mechanism, and a user confirming it works) but **under-documented in the current primary how-to guide** — flagged here rather than silently resolved.

**A related, distinct capability**: Studio can also act as an **MCP server itself** (not just an MCP client connecting to external tool servers), via an opt-in "MCP control plane" (PR #7191, read via GitHub) that lets an MCP client inspect/operate Studio's own training, export, and recipe services [^32]. It's opt-in via `UNSLOTH_STUDIO_ENABLE_MCP=1`, mounted at `/mcp`, and "When `UNSLOTH_STUDIO_MCP_TOKEN` is set the endpoint requires an exact bearer token. Without that setting the endpoint remains intended for a local Studio process only" [^32] — and per the review thread, the code was hardened during review to fail startup with a `RuntimeError` if the token is unset while the plane is enabled, and to authenticate WebSocket connections (an initial version only checked HTTP-scope requests, which the reviewer flagged as a bypass, then confirmed fixed) [^32]. This PR's merge status was **not confirmed** in what I fetched — it was mid-review at the point this page was read — so treat "Studio-as-MCP-server" as a real, in-development capability rather than a confirmed-shipped one. **UNVERIFIED**: exact merge/release status of PR #7191.

## What Vela should take

1. **Per-model capability badges in the model picker** (Vela: the model/endpoint selector in the chat composer or a model-settings panel). Unsloth's TIGHT/OOM-style fit indicator on GGUF variants is directly applicable to Vela's local llama.cpp models — show, at selection time, whether a quant fits the user's detected VRAM/RAM, not just its name and size [^8].
2. **Unified model picker across local and remote backends** (Vela: the model selector component). Unsloth folds local GGUF, HF Hub search, and externally-connected providers (OpenAI/Anthropic/Ollama/vLLM) into one combobox with grouping (local vs. connected) [^14][^12]. Vela already talks to llama.cpp and OpenAI-compatible endpoints — this argues for one selector object with a `source`/`state` field rather than separate local-vs-remote UI paths.
3. **Explicit, named model state machine (downloading → loading → ready) surfaced to the user** (Vela: whichever surface shows "model loaded" status, e.g., a status chip near the composer). Unsloth shows discrete states with a visible confirmation when a model is actually ready to chat, rather than a spinner-then-nothing [^10].
4. **Settings as its own multi-tab area, not a single monolithic modal** (Vela: Settings surface). Unsloth's System/Connections-tabbed settings, reached via `Settings → <tab>`, scales better than a single dialog once you have per-provider config (endpoint, auth, capability toggles) — relevant since Vela already stores credentials per-provider in the OS keychain [^12][^18].
5. **A visible, cancelable long-operation surface with a save-vs-discard choice on stop** (Vela: a generation-in-progress or download-in-progress indicator). Unsloth's pattern — persistent progress affordance, explicit cancel with confirmation, and (for training) a "stop & save" vs. "stop, discard" choice — maps to Vela's model-download flow (llama.cpp GGUF pulls) and could inform how an interrupted generation is framed (keep partial output vs. discard) [^3].
6. **Inline, blocking-until-valid form validation for irreversible/expensive actions** (Vela: any "start download" or "connect endpoint" action). Disabling the primary action until required fields validate, with inline errors at the field, is a small, well-evidenced pattern worth copying for Vela's "add endpoint"/"add model" flows [^3].
7. **Chained, human-readable error causes for setup/connection failures**, not just a generic toast (Vela: endpoint connection errors, model load errors). Unsloth's install log format (`Failed to fetch: <url>` → `<cause>` → `<cause>`) is more diagnosable than a single opaque message, and directly useful for Vela's "can't reach this OpenAI-compatible endpoint" case [^16].
8. **One local port, path-routed dialects, one bearer key** (Vela: if/when Vela exposes its own local API for other tools, or documents how it talks outbound to dual-format backends). Unsloth's "speak two dialects on one port, route by path, authenticate with one shared key" is a clean, minimal-surface-area pattern — no separate ports or processes per API style [^20].
9. **The confirmed `tool_choice` translation table** (Vela: any tool-calling/agent layer that needs to bridge Anthropic- and OpenAI-style tool semantics). `auto→auto`, `any→required`, `{type:"tool",name}→{type:"function",function:{name}}`, `none→none` is a verified, reusable reference if Vela ever needs to normalize tool_choice across provider families [^20].
10. **State the base_url asymmetry in the connection-setup UI copy itself**, not just in troubleshooting docs (Vela: the "add endpoint" flow for Anthropic-compatible vs. OpenAI-compatible backends). Unsloth's own docs only show this correctly by example (bare URL for Anthropic, `/v1`-suffixed for OpenAI) rather than calling the asymmetry out explicitly anywhere I found — Vela can do better by stating the rule inline where the user types the URL, pre-empting exactly the class of error the coordinator flagged [^23][^26].
11. **Bind-address-driven default security posture with a request-level-override-proof policy** (Vela: any local code-execution, MCP, or tool-calling feature, especially if Vela ever supports LAN/remote access to a running instance). "Loopback = tools on by default; non-loopback = tools off by default; the resolved policy can't be flipped per-request" is exactly the shape a Vela sandbox/tool policy should copy, along with the explicit rationale (leaked key + exposed port = RCE) [^20].
12. **A four-level, clearly-labeled permission selector for agent/tool capability** — Ask / Approve for me / Off / Full access — rather than a binary on/off toggle (Vela: any tool-calling, MCP, or code-execution permission surface Vela builds). This is a concrete, already-designed UI vocabulary Vela can adapt directly [^27].
13. **Defense-in-depth as the sandbox design posture, not a single filter** (Vela: any sandboxed code-execution or tool-call surface). The lesson from issue #4818/PR #4827 is specific: layer tokenization correctness, OS-level privilege denial (e.g., `PR_SET_NO_NEW_PRIVS`-equivalent), static analysis, and an expanded blocklist — and still describe the result as mitigation, not closure, in both public communication and internal threat modeling [^28][^29][^30].
14. **Canvas's two-mode split (auto-rendered preview vs. Code view) for any model-generated interactive output** (Vela: if Vela ever renders model output beyond markdown/plain text, e.g. generated HTML or diagrams). Small, well-scoped, already-proven UI pattern [^1][^27].
15. **MCP connection UI: OAuth-first with a header-based fallback, per-server toggle plus a master toggle** (Vela: an MCP settings panel, if planned). Unsloth's flow — base URL, OAuth sign-in for browser-auth servers, custom-header auth for token servers, individual server toggles under one master switch — is a directly reusable shape [^24].

## What Vela should not take

- **Nothing about the training/fine-tuning surface itself** — LoRA/QLoRA hyperparameter forms, dataset column-mapping, Data Recipes' graph-node dataset builder, GPU-utilization/gradient-norm charts, YAML config import/export. Vela is a chat client with no training loop; importing this would add an entire unrelated product surface [^3].
- **The multi-page workbench IA wholesale.** Studio's top-level areas (Chat / Images / Train / Data Recipes / Export) exist because it's simultaneously a trainer, an image generator, a data tool, and a chat client. Vela is chat-first; copying that many top-level nav destinations would import complexity Vela doesn't need. What transfers is the *shape* of "Settings as its own tabbed area" and "model as an object with state," not the specific set of tabs.
- **Running as a local HTTP server with browser-based auth (password + JWT, optional Cloudflare tunnel for remote access) by default.** This exists in Studio because it's fundamentally a local web app that can also be exposed over the network. Vela is a native desktop app; a local password/JWT login screen and a "publish over HTTPS" tunnel feature would be pure overhead for a single-user desktop chat client. If Vela deliberately adds a local-API-server feature later (e.g., so Claude Code can use a Vela-managed model, mirroring Unsloth's `unsloth start`), it should adopt Unsloth's bind-address-gated tool policy from day one rather than defaulting open [^2][^1][^20].
- **AGPL-licensed UI code as a model for architecture decisions** — irrelevant to Vela's design but worth noting: Unsloth deliberately splits license by component (Apache-2.0 core vs. AGPL-3.0 Studio UI) for business reasons specific to their fine-tuning-library monetization; not a UX or architecture lesson for Vela [^1][^2].
- **The observed reliability rough edges** (transient error toasts that vanish before they can be read; duplicate-render bugs on tab-switch) are failure modes to explicitly avoid, not features to take — flagged here as anti-patterns, confirmed by real user reports [^13].
- **Provider/tool features tied to training-adjacent workflows** — code-execution sandboxing for "self-healing tool calling," Data-Recipes-style document-to-dataset generation, and model export-to-GGUF are all downstream of Studio being a training tool. Vela already talks to inference endpoints; it doesn't need a dataset pipeline or export format converter.
- **Naive string/substring command filtering as a security boundary.** Unsloth's own published tool-calling tutorial code ships exactly this anti-pattern in its example `terminal()` function — blocking `rm`/`sudo`/`dd`/`chmod` by checking `if "rm" in command or "sudo" in command...` [^26] — which is precisely the class of check issue #4818 showed was bypassable in the real product [^28][^29][^30]. If Vela ever sandboxes tool/code execution, it should start from process-level isolation (OS privilege restriction, resource limits, real tokenization) and treat substring blocklists as, at best, a defense-in-depth layer, never the only one.
- **Marketing/documentation getting ahead of, or lagging behind, shipped reality.** Two independent examples surfaced in this research: a "fixed" sandbox bug whose own reporter said "still not there" the day after closure [^29][^30], and a stdio MCP feature that shipped and was confirmed working months before the primary how-to doc caught up to mention it [^24][^31][^27]. Whatever Vela ships around tool-calling/sandboxing/agent integration, keep the changelog and the primary how-to docs matched to actually-verified behavior, not to what was intended or partially shipped.
