THE BOUNDARY, STATED BEFORE THE EVIDENCE
--------------------------------------------------------------------------------
Phase A ships NO HTTP CLIENT. Not in the Rust core, not in any domain crate, not
in the renderer. `vela-providers` defines the `ModelProvider` trait and one
in-process `EchoProvider`; there is no `openai_compatible.rs` yet — that is
Phase B.

Therefore no Vela code opened a socket to any of the four servers. The only Vela
code that can consume an endpoint today is the configuration / validation /
security-posture layer (`vela-settings`, `vela-core`), which takes the endpoint's
URL and decides whether the configuration is valid, usable, and risky.

  PROVED BY THIS FILE
    * Each live matrix endpoint's URL is accepted by Vela's real validator.
    * With a COMPLETELY EMPTY keychain, each is `usable: true` and
      `credentialCheck: satisfiedWithoutCredential` — "no API key" is a
      first-class state, as the brief requires, not an error.
    * Each is scored `RiskLevel::None` because it is loopback; the same
      configuration on a remote host is scored `Elevated`, so the silence is a
      decision rather than a blind spot.
    * There is no HTTP client anywhere in the workspace — asserted against every
      Cargo.toml, not narrated.

  NOT PROVED BY THIS FILE, AND NOT PROVABLE IN PHASE A
    * That Vela can talk to these endpoints.
    * That Vela parses, degrades, or recovers correctly against any of them.
      Every graceful-degradation claim in RESULTS.md is a claim about what the
      ENDPOINTS did and what a naive consumer suffered — never about Vela's
      provider layer, which does not exist yet. The transcripts are the
      specification Phase B has to satisfy, not a report card on Phase A.

ONE MORE LIMITATION, FOUND WHILE RECORDING
--------------------------------------------------------------------------------
The harness sends no CORS headers and answers an OPTIONS preflight with 405 (see
each profile's 00-server-and-capabilities.txt). The frontend is required to run
standalone in a browser via `pnpm dev` so it can be screenshotted headlessly —
and a browser-hosted renderer therefore cannot call these endpoints directly.
This is consistent with the architecture (HTTP belongs in the Rust core, behind
the IPC bridge), but it does mean the browser-mode UI can never be exercised
end-to-end against this harness. Browser-mode chat will need a mock adapter
response, not a live endpoint.
