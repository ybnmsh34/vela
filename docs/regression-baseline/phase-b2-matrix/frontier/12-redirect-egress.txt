GATE M Part 1 (Phase B2) — profile: frontier — case 12-redirect-egress: a 3xx must not carry the request — or the credential — off the configured authority
================================================================================

PURPOSE   The round-3 panel's security FAIL. `reqwest`'s cross-host protection strips five headers and none of them is `x-api-key`, `x-goog-api-key` or anything an `Auth::ApiKeyHeader` binding names; `make_referer` keeps the query string. So a redirect from the configured endpoint handed the user's key to a host they never configured, on the first request of a healthy turn.
SUBJECT   Vela's own provider stack (vela-providers::OpenAiCompatibleProvider)
ENDPOINT  tests/harness/mock-provider, profile `frontier`, a real OS process on loopback
HONESTY   VERIFIED-BY-FAKE. The endpoint is a deterministic mock; no model produced
          any byte below. Nothing here is evidence about a real model.

  THE SUBJECT IS THE THIRD PARTY, not Vela. Every assertion below is made against
  what a recording listener on a port the user never configured actually received:
  accepted connections, raw bytes, and the literal request the client wrote. A
  credential smuggled in a `Referer`, in a query string, or in a header nobody
  thought to enumerate is caught the same way, because nothing is enumerated.
  The canary is masked wherever this file prints received bytes. It is a fake that
  was never a credential for anything, and the transcript is still committed.
