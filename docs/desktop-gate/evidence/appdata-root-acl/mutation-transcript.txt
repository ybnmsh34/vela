N3  a DENY ace counted as granting  (ace::verdict)
    cargo test -p vela-privatefs --lib
    => 2/2 runs, 2 tests:
       a_deny_ace_for_a_foreign_principal_is_not_a_foreign_reader
       a_deny_ace_an_administrator_added_survives_the_walk

    THE ONE WITH TEETH -- BUT NOT FOR THE REASON GIVEN HERE IN ROUND 2.

    Round 2 said the consequence was "Vela would decline to start over an ACL
    stricter than the one it demands". That is NOT REACHABLE, and the check is
    easy: every describe() whose answer can produce a refusal (enforce, and
    make_file_private) runs immediately after apply(), which builds a fresh
    two-ACE DACL from NULL. No pre-existing deny entry survives to be read back
    on those paths.

    The reachable consequence is worse. The one describe() that reads a DACL
    nobody has just replaced is the `before` inside repair_within, and there a
    false Foreign does not refuse -- IT REPAIRS. A directory an administrator
    had locked a group out of would have had that lockout SILENTLY DELETED by a
    routine startup, and the read-back would have confirmed the result as
    private, because it is. Vela would have widened a path in the name of
    narrowing it.

    The round-2 test asserted the unreachable property (is_private() on a
    hardened directory). It has been replaced by one that drives repair_entries
    over a directory carrying a real deny ace added with icacls and asserts the
    ace is still there afterwards.
